## perf 計測メモ（2026-11-19 07:52 JST、0.3.0 = main@b06ff5a、本番 950・perf 150・perf_p50 408,294µs）

- 計測手段: docker ドライバ（本番相当 2CPU/1GiB/256pids）×4、キットの `runBenchmark` を直接叩くローカル計測（taskset 2CPU、A/B 交互）、callgrind（命令数）、strace -c（syscall 数）、/proc（ページフォルト・CPU 時間）。
- docker ×4 の幾何平均 p50: 231.6 / 252.9 / 249.2 / 235.5 ms（中央値 ≈ 242 ms）。本番 408 ms は約 1.7 倍＝4 ワークロード一様に遅いと見ると本番の点は push≈45・clone≈30・read≈38・write≈37（計 150）で一致。
- フォージ側のコスト（ワークロード全体）:
  - CPU: 全ベンチを通してフォージは約 0.55 秒（stime > utime）。read 1 回 ≈ 18k 命令（≈ 5〜7µs）、write ≈ 60k 命令、push ≈ 250k 命令（≈ 70µs、inflate 45%・SHA-1 31%）、clone の各リクエストはほぼ 0（キャッシュ済み）。
  - syscall: read/write とも 1 リクエスト = recv 1 + send 1（futex なし）。POST は本体が別セグメントで届くと recv が 1 回増える（クライアント側の書き方なので変えられない）。
  - ページフォルト: read ≈ 90・write ≈ 380・push ≈ 600（ワークロード全体）。clone ≈ 2,200 は round 1 の接続スレッド生成（約 100 接続）で、中央値には入らない。
  - strace の時刻: push 1 回のうちサーバ処理は GET ≈ 60µs・POST ≈ 150µs、残り ≈ 1.6ms はクライアント（git-client の JS と fetch）。
- 試した最適化: inflate のハフマン表（固定表の静的キャッシュ＋表幅を最長符号に合わせる）→ push の命令数 −14%（59.4M → 51.1M）だが、壁時計は A/B 5 回で差なし（A 中央値 251ms・B 255ms）→ 規則どおり不採用（revert）。
- 結論: 時間の 9 割以上はクライアント（Node の fetch・undici）とネットワーク。サーバ CPU をゼロにしても各ベンチ数 % 以下で、ローカルのノイズ（±15%）の下。本番のばらつきはハウス自身で perf_p50 26%（ワークロード別 18〜55%、calibration.json）。賞金ラインとの差（8%）はこのノイズの内側。
- 最終順位は締切後の 3 インスタンスの平均なので、練習の 1 回の perf を引き直すための再提出は最終結果に効かない。
- 試していないもの（本番 gVisor でしか効果が測れず、ローカルでは検証不能のため見送り）: epoll 化（clone の 100 スレッドの起床回数削減）、POST 本体待ちの短いスピン。
